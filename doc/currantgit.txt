COMMANDS                                                        *currantgit-commands*

:Git                                                            *:Git*
                        With no arguments, open the repository status surface
                        for the current working directory.

:Git status               Open or refresh the status surface.
:Git log                  Open the read-only commit log (latest 50 commits).
:GitActivity              Open the optional read-only Git command activity log.
:Git {args}               Run an arbitrary Git command and display its output
                          in a CurrantGit command surface.

The command surface is intentionally small in the bootstrap implementation.
`:Git` remains the escape hatch for commands that do not yet have a dedicated
item action.

`:Git` respects window-opening command modifiers the same way fugitive's
`:Git` does: `:vertical Git`, `:tab Git`, `:horizontal Git`, `:topleft Git`,
and similar open the surface in a new split/tab instead of replacing the
current window. With no modifier, the surface replaces the current window,
same as a plain `:edit`. This only applies to the top-level `:Git` command;
navigating within a surface (refresh, opening a diff from a status item, ...)
never opens a split.

===============================================================================
STATUS                                                          *currantgit-status*

The status surface is buffer-native and read-only. It exposes semantic change
items rather than making rendered lines the source of truth.

Changes are grouped into semantic sections when present: staged changes,
unstaged changes, untracked files, and conflicts. Sections are native folds;
the usual |fold-commands| work without a CurrantGit-specific replacement.
Section headings include their current item count, while the item identity and
available actions remain attached to the item below the heading. On a clean
repository the "Changes" heading and its sections are omitted entirely rather
than shown with a zero count.

Status keeps itself current the way fugitive's does. Writing a file inside
the repository (|BufWritePost|), running a shell command (|ShellCmdPost|), or
Neovim regaining focus (|FocusGained|) marks it stale, and it reloads the
next time you enter it (|BufEnter|, |TabEnter|), or at once if it is the
current buffer. Entering a status that has not changed runs no Git command.
It never reloads in the middle of a visual selection; it waits for the next
enter instead. `r` still refreshes on demand.

                                                        *currantgit-quit*
`gq` quits any CurrantGit surface (status, diff, log, commit, activity, the
deleted-file view, blame, the diff split, the conflict resolver). A surface
opened in its own split or tab closes it; otherwise the window returns to
the buffer the first CurrantGit surface replaced in it (an empty buffer if
there was none).

On a change item:

<CR>                    Open the file. Deleted files open their last
                        available Git revision read-only.
d                       Show the file diff.
D                       Open old | new side by side in a new tab, in native
                        |diff-mode|. See |currantgit-diff-split|.
b                       Open the blame companion.
s                       Stage the file.
u                       Unstage the file.
-                       Toggle the file's staged state.
X                       Discard working-tree changes after confirmation.
r                       Refresh the status surface.
cc                      Commit. See |currantgit-commit|.
ca                      Amend the last commit and edit its message.
ce                      Amend the last commit, keeping its message.
cw                      Reword the last commit; staged changes stay staged.
cvc  cva                Commit or amend with the diff shown below the
                        message (`git commit -v`).
g?                      Open this help section.
=                       On a staged or unstaged change item, toggle that
                        file's diff inline beneath the row: index-vs-HEAD for
                        a staged item, worktree-vs-index for an unstaged one.
                        A file with both staged and unstaged changes renders
                        as two rows, and each toggles independently using its
                        own row's comparison. Not offered for untracked or
                        conflict items. On a section heading, `=` instead
                        toggles that section's native fold, same as an
                        appropriate |fold-commands| would. The inline diff is
                        ordinary read-only buffer content: it can be
                        searched, yanked, and its own hunks are native folds
                        nested inside the section's fold. Expansion state
                        survives a refresh for changes that still exist and
                        is dropped for changes that no longer do. Inside an
                        inline diff, `s` and `u` act on the hunk under the
                        cursor (as in the diff surface) and refresh status.

Visual mode (|linewise| or characterwise) applies `s`, `u`, `-` and `X` to
every unique item on the selected lines:

{Visual}s               Stage every selected file in one `git add`, or every
                        selected unstaged inline hunk as one patch.
{Visual}u               Unstage every selected file in one
                        `git restore --staged`, or every selected staged
                        inline hunk as one reverse patch.
{Visual}-               Toggle each selected file, as `-` does: files with
                        staged changes unstage, the rest stage (at most one
                        unstage call, then one stage call).
{Visual}X               Discard every selected file's working-tree changes
                        after a single confirmation listing every file.

Each file is passed as its own `:(literal)` pathspec. Items an action does not
apply to (e.g. an already fully staged file under `s`) are skipped and named in
a warning. A selection that mixes file rows and hunks is refused rather than
guessed at. If Git rejects a batch (for example, a selected file vanished since
the last refresh), nothing in that batch is applied.

Below the status body, an "Available actions" list shows the keys that apply
to the item under the cursor. It is generated from the same action metadata
as the mappings, so it is a hint, not a second keymap definition. It is
ordinary read-only buffer text: it can be searched and yanked, sits outside
the status folds, and is not rewritten while the cursor is inside it.

Integrations can use `require('currantgit').discovery()` for structured
`id`, `key`, `label`, and `desc` entries, or
`require('currantgit').which_key()` for a WhichKey-compatible mapping table.
Both projections are contextual to the item under the cursor. They return an
empty table when called for an ordinary or invalid buffer.

Status metadata uses colorscheme-friendly highlight groups. Users may define
these groups before setup to override the default links:

CurrantGitRepository        Repository heading (Title)
CurrantGitBranch            Branch metadata (Identifier)
CurrantGitHeading           Status and section headings (Directory)
CurrantGitCount             Change counts (Number)
CurrantGitStatusAdded       Added markers (DiffAdd)
CurrantGitStatusDeleted     Deleted/conflict markers (DiffDelete)
CurrantGitStatusModified    Modified markers (DiffChange)
CurrantGitStatusRenamed     Renamed/copied markers (Special)
CurrantGitStatusUntracked   Untracked markers (Comment)
CurrantGitPath              Repository-relative paths (Normal)
CurrantGitHelpHeading       "Available actions" heading (Comment)
CurrantGitHelpKey           Action keys (SpecialKey)
CurrantGitHelpDescription   Action descriptions (Comment)
CurrantGitActivitySuccess   Activity success marker (DiagnosticOk)
CurrantGitActivityFailure   Activity failure marker and exit code (DiagnosticError)
CurrantGitActivityTime      Activity timestamps (Comment)
CurrantGitActivityDuration  Activity durations (Number)
CurrantGitActivityCommand   Activity argv (Statement)
CurrantGitActivityOutput    Folded command output (Comment)
CurrantGitActivityStderr    Failed commands' stderr (DiagnosticWarn)

Diff text is syntax highlighted in the changed file's own language wherever
CurrantGit shows it: the diff surface, inline `=` diffs in status, and the
commit view. Each hunk's old and new sides are parsed separately with the
file's treesitter parser, so multi-line strings and comments parse as they do
in the file. Added and removed rows get line backgrounds. Files with no
installed treesitter parser keep the backgrounds without token colours.
Regions over 5000 lines skip token highlighting. On the diff surface these
highlights replace the regex `diff` syntax ('syntax' is OFF); the filetype
stays `diff`.

CurrantGitDiffAdd           Added rows (DiffAdd)
CurrantGitDiffDelete        Removed rows (DiffDelete)
CurrantGitDiffAddSign       The `+` prefix (Added)
CurrantGitDiffDeleteSign    The `-` prefix (Removed)
CurrantGitDiffHunk          `@@` hunk headers (Statement)
CurrantGitDiffHeader        `diff --git`/`index`/`---`/`+++` lines (Comment)

The diff action opens a read-only diff surface. Hunk headers are native fold
roots, so |fold-commands| can collapse or reopen each hunk.
Each hunk is also a stable semantic item with source ranges and collapse,
stage, and unstage capabilities. On a working diff, `s` stages the current
hunk. On a staged diff, `u` unstages the current hunk. These actions send the
exact hunk patch to Git through stdin; they do not construct shell commands
from rendered text. In visual mode, `s` and `u` apply every selected hunk
(across files) as a single patch, so Git applies all of them or none.
A successful mutation refreshes the same diff projection.
If Git rejects the patch, CurrantGit reports the failure and leaves the
projection and repository state untouched.

On a deleted item, <CR> opens the last available Git revision in a read-only
`currantgit://deleted/...` buffer. CurrantGit does not create an empty buffer
for a path that no longer exists.

The `b` action (or `:Git blame [path]`) opens a blame annotation window to
the left of the source, like fugitive's `:Git blame`. It holds one row per
source line and does not repeat the source text. The first row of each
same-commit run shows the short commit ID, author, and author date. The rest
of the run shows a `│` guide in that commit's colour, so each run reads as
one block. Each commit gets its own colour (derived from its hash when
'termguicolors' is set), shared by every run it owns.

The blame and source windows are bound with 'scrollbind' and 'cursorbind',
so scrolling or moving in either keeps the other aligned. While bound, the
source window has 'nowrap' and 'nofoldenable', because wrapped or folded
lines would break the 1:1 alignment. Its original options come back when
blame closes. Running blame again for the same file, including from the
blame window, replaces the existing annotation window.

`gq` closes the blame window and returns to the source buffer. `<CR>` on a
row opens its commit in the blame window, which is unbound and widened while
it shows the commit. CTRL-O returns to blame and re-binds it.

Blame highlight groups:

CurrantGitBlameHash         Commit IDs without 'termguicolors' (Identifier)
CurrantGitBlameAuthor       Author names (Normal)
CurrantGitBlameDate         Author dates (Comment)
CurrantGitBlameUncommitted  Lines not committed yet (Comment)

                                                    *currantgit-activity*
`:GitActivity` shows the bounded command ledger, newest first. Each row is
one Git command: a ✓/✗ status marker, the local HH:MM:SS start time, the
duration, and argv without the leading `git`. Failed rows end in `exit N`.
A repository path heading appears whenever the working directory changes
from the previous row. Command output sits in a native fold under its row,
closed by default; failed commands start expanded so their stderr is
visible. NUL separators from `-z` commands render as line breaks and other
control bytes as `<xx>`, so the buffer never contains raw control bytes.

Each row is an `activity:<n>` item in `b:currantgit_line_items`, where `n`
is the command's position in the ledger. `<CR>` or `=` toggles the row's
output (ordinary `zo`/`zc` work too), `r` refreshes, and `g?` opens this
help. The "Available actions" list sits below the ledger, as in status.
It is an inspection surface, not a replacement for the status projection.

COMMITTING                                                   *currantgit-commit*

The commit keys in status (`cc`, `ca`, `ce`, `cw`, `cvc`, `cva`) match
fugitive's. They run `git commit` with the matching options and let Git do
the rest: when Git wants a message, it opens in a split here.

This works for every `:Git` command that needs an editor, not only commits:
`:Git commit`, `:Git merge` without `-m`, `:Git tag -a`, `:Git rebase -i`
(the todo list opens as a `gitrebase` buffer). CurrantGit sets `GIT_EDITOR`
and `GIT_SEQUENCE_EDITOR` for the Git commands it runs, which take precedence
over `core.editor`, `sequence.editor`, `$VISUAL` and `$EDITOR`. Git still
writes the file, so its templates, merge messages, `commit.template` and
hooks all apply as usual.

Finish by closing the buffer. Git reads the file as it is on disk at that
moment, exactly as with a terminal editor:

:wq                     Save and hand the message to Git.
:q!                     Discard your edits. Git sees its own template, which
                        has no message, and aborts the commit.

An empty message (only comments) aborts a commit, and an empty todo list
aborts a rebase. Both are Git's own rules. There is no `:cq`: to abort, close
without a message. After a commit, the first line of Git's output (for
example `[main 1a2b3c4] Subject`) is shown and status refreshes. Git's
refusals, such as "nothing to commit", are shown as errors and change
nothing.

CONFLICTS                                                 *currantgit-conflicts*

Each row in the status Conflicts section is a `conflict-file:<path>` item,
and each conflict region inside it is a `conflict:<path>:<n>` item. This
resolver never writes the index or saves the file: region choices edit the
result buffer only, and you save with `:w` as usual.

Sides come from the index stages, not from re-reading markers you may already
have edited: `git ls-files -u` says which stages exist, `git merge-file
--object-id` re-merges them (honoring `merge.conflictStyle`, which decides how
many regions there are), and the panes show `git show :1:`/`:2:`/`:3:<path>`.
Region locations come from the markers still in the worktree file. A region
whose markers are gone counts as resolved.

The row shows `resolved/total`, or why there is no count: `deleted by us`,
`deleted by them`, `deleted by both`, or `binary`.

In status:

<CR>                    On a conflict row, open the resolver in a new tab.
]x  [x                  Jump to the next/previous conflict row. Stops at the
                        ends, like |]c|.
s  -  d  b              Stage, toggle, diff, and blame behave as on a change
                        item (staging is `git add`, i.e. Git's own "mark
                        resolved"). Discard and unstage are not offered.

The resolver is ours (stage 2, read-only) | result (the real file) | theirs
(stage 3, read-only), all in native |diff-mode|, so |]c| and |[c| work. With
three diff buffers, |do| and |dp| need a buffer argument, e.g.
`:diffget currantgit://conflict/ours/<path>`. A missing side (delete/modify)
is an empty pane labelled "(deleted)". Save and undo are Vim's own.

In the resolver:

]x  [x                  In the result pane, jump to the next/previous
                        conflict region.
gb                      Show or hide the merge base (stage 1) under the
                        result pane. It is read-only and stays out of diff
                        mode.
gq                      Close the resolver tab from any pane. Unsaved edits
                        to the result stay in its (hidden) buffer.
gl                      Switch between three panes and the result alone
                        (no diff mode; colors, labels, counts and every key
                        below still work). The default is the
                        `conflict.layout` option: "three" or "single".

With the cursor inside a conflict region in the result pane:

co                      Take ours.
ct                      Take theirs.
cb                      Take both, ours first.
cB                      Take both, theirs first.
c0                      Take the base. Only diff3/zdiff3 markers carry a
                        region's base; with merge-style markers this refuses
                        and points you to `gb`.

Each choice replaces the whole region, markers included, in one undoable
change: `u` brings the markers back. A resolved region is labelled
"✓ ours", "✓ theirs + ours", and so on, and the winbar count goes up. The
region under the cursor is drawn with stronger tints. Outside a region these
keys are Vim's own |c| with a motion (`cb` still changes back a word); see
docs/decisions/0014. Marking the file resolved (`git add`) is still `s` in
status.

Presentation: each side has its own colors in its pane and inside the
result's conflict blocks, filler lines are hatched (`diff:╱` in
'fillchars'), marker lines keep their real text with an end-of-line label,
and the result winbar shows "n of m resolved" as you edit. Word-level
highlights come from your 'diffopt' (`inline:word` or `inline:char`);
CurrantGit does not change that global option. Override these groups to
restyle it. The tints are mixed from your colorscheme's DiagnosticInfo
(cool) and DiagnosticWarn (warm) colors over Normal, and recomputed on
|ColorScheme|:

CurrantGitConflictOurs          Ours lines (cool tint)
CurrantGitConflictOursText      Changed text on ours lines
CurrantGitConflictOursLabel     The "ours" marker label
CurrantGitConflictTheirs        Theirs lines (warm tint)
CurrantGitConflictTheirsText    Changed text on theirs lines
CurrantGitConflictTheirsLabel   The "theirs" marker label
CurrantGitConflictBase          Base text in diff3/zdiff3 blocks (dimmed)
CurrantGitConflictBaseLabel     The "base" marker label
CurrantGitConflictMarker        Marker lines (dimmed, still real text)
CurrantGitConflictFiller        Hatched filler (faint, instead of DiffDelete)
CurrantGitConflictResult        Diff colors in the result pane (none, so
                                only the region tints show)

Markers are assumed to be the default 7 characters; a custom
`conflict-marker-size` attribute is not read yet.

DIFF SPLIT                                              *currantgit-diff-split*

`D` (`item.diff_split`) on a staged or unstaged change row opens a new tab
with the old side on the left and the new side on the right, in native
|diff-mode|, so |]c|, |[c|, |do| and |dp| work. The comparison follows the
row's section, like `=`:

staged                  `HEAD:<path>` | `:0:<path>`, both read-only.
unstaged                `:0:<path>` (read-only) | the real worktree file,
                        which you can edit and save as usual.

Renames and copies read the old side from the source path. A missing side
(an added file has no HEAD side; a deleted file has no new side) is an empty
read-only pane whose winbar says "(none)" or "(deleted)". Winbars name each
side: `HEAD <short sha>`, `index`, `worktree`. Read-only sides are
`currantgit://diff/<side>/<path>` buffers. Opening the split never writes the
index or the worktree. Untracked and conflict rows do not offer `D`. `gq`
in either pane closes the tab; the mapping is removed from the worktree
file once it leaves the split.

It uses the resolver's presentation: hatched filler and tints mixed from
DiagnosticWarn (old) and DiagnosticInfo (new), recomputed on |ColorScheme|:

CurrantGitDiffOld               Old-side diff lines (warm tint)
CurrantGitDiffOldText           Changed text on old-side lines
CurrantGitDiffNew               New-side diff lines (cool tint)
CurrantGitDiffNewText           Changed text on new-side lines
CurrantGitDiffFiller            Hatched filler (faint, instead of DiffDelete)

LOG                                                             *currantgit-log*

:Git log projects commits into a read-only, searchable, yankable buffer. Each
row shows a short object ID, author date, author, and subject. The semantic
commit item retains the full object ID, parents, author name/email, ISO author
date, subject, repository, and stable `commit:<full-object-id>` identity.
Items are exposed through `b:currantgit_items`; `b:currantgit_line_items` maps
the visible rows to those items. Rendered text is never an action target.

<CR>                    Open the selected commit's stat and patch using the
                        shared commit view (action ID: `commit.open`).
r                       Refresh this log with its original arguments and
                        repository. Retain the selected commit when present.
g?                      Open this help section.

Ctrl-O returns from a commit to the log and restores the cursor. Ctrl-Shift-I
moves forward again. The "Available actions" list and the public
discovery()/which_key() projections use the action registry. Headers and empty results have no
commit action. Log actions do not stage, reset, or otherwise mutate Git state.

The default limit is 50 commits. Selection arguments supported by this surface:

  -n N, -nN, -N, --max-count N, --max-count=N
  --all, --reverse, --first-parent, --no-merges, --merges
  --skip=N, --since=VALUE, --until=VALUE, --author=VALUE, --grep=VALUE
  revisions/ranges and -- followed by repository-root-relative paths

An explicit count overrides the default. Examples: >
  :Git log -n 10
  :Git log HEAD~5..HEAD
  :Git log -- lua/currantgit/init.lua
<
Output options such as --graph, --oneline, --format, and --patch, and any other
unsupported option, use the ordinary command surface with the original Git
arguments. They are not silently rewritten into semantic rows. This bootstrap
command still splits arguments on whitespace; quoted values containing spaces
are not supported. Pass a Lua argv table to require('currantgit').git({...})
when an argument contains spaces.

A successful empty selection displays "no commits". Git errors (including
unborn HEAD for a plain log) are reported without replacing the current view.
Log responses are ignored if superseded or if the user has left the originating
window/buffer before completion. One log buffer is reused; this slice does not
provide pagination, graph lanes, revision editing, or independent log tabs.

NAVIGATION                                               *currantgit-navigation*

CurrantGit-managed views use the regular Neovim navigation keys for local view
history:

CTRL-O                  Move back through CurrantGit view history.
CTRL-SHIFT-I            Move forward through CurrantGit view history.

The view history preserves the buffer, cursor, and window view. If a reused
surface became shorter since it was recorded, CurrantGit restores the nearest
valid cursor and view instead of replaying stale coordinates. Invalid deleted
buffers are skipped. When the local CurrantGit history is exhausted, the key
falls through to normal Neovim jump navigation. CurrantGit does not globally
redefine these keys.

This documents CurrantGit’s boundary behavior; see |:help jump-motions| for
Neovim’s underlying navigation semantics.

ACTIONS                                                     *currantgit-actions*

Actions are capabilities of semantic items. Mappings, discovery text, and
future WhichKey integration are projections of the same action metadata.

An action may be available for a change, hunk, commit, blame line, person, or
another item kind. Extensions should target stable item IDs and capabilities,
not rendered line numbers.

`require('currantgit').rpc()` creates an in-process protocol adapter. Requests
have IDs and methods, responses carry structured errors or revisioned results,
and `rpc.capabilities` reports the negotiated version and capabilities.
Handlers are explicitly registered; the adapter does not evaluate arbitrary
Lua or shell text. Event subscribers receive revisioned event envelopes.
